PR #10 — Stone 6: make Main.Api host port and SSH port configurable

Workflow · branch stone6-configurable-deploy-ports · 5 files, +94 / -25 · 1 commit · #10 on GitHub ↗

What this PR does. Two values in Main.Api's deploy/ were hardcoded — the host port the container publishes (8080) and the SSH port provision.sh uses (22). This makes both configurable via deploy/.env (WORKFLOW_HOST_PORT, VPS_SSH_PORT), so a busy 8080 or a non-standard SSH port no longer blocks a deploy. filigrane stays local; this is a deploy-config stone.

Start here → deploy/docker-compose.yml — the ${WORKFLOW_HOST_PORT:-8080} change is load-bearing; the SSH-port change is a parallel, self-contained thread through provision.sh.

Read carefully

Ordering dependency. In Stage 3, write_env WORKFLOW_HOST_PORT runs before the scp that ships .env to the VPS. Writing it after the copy would silently deploy on 8080.
Defaults after ask. ${VPS_SSH_PORT:-22} / ${WORKFLOW_HOST_PORT:-8080} are applied right after ask, which returns empty on a first-run Enter — without them ssh -p "" / published: "" would break.
Scope. The SSH-port path has no automated test (no remote() helper refactor, by decision) — verified manually against a real VPS.

How to test

Automated (no Docker daemon needed):
  • bash deploy/test/compose-port.test.sh — passes locally; asserts the published port tracks WORKFLOW_HOST_PORT, defaults to 8080, and keeps the loopback bind + container target.
Demo the render:
  • WORKFLOW_HOST_PORT=9090 docker compose -f deploy/docker-compose.yml config → published: "9090".
  • Unset it and the same command shows published: "8080".
Exercise the wizard:
  • Re-run ./deploy/provision.sh — it now prompts for VPS_SSH_PORT (Stage 1) and WORKFLOW_HOST_PORT (Stage 3) and writes both to deploy/.env.
SSH port — manual only. Point provision.sh at a VPS whose SSH listens on a non-22 port; confirm the connectivity check, clone, scp, compose-up, and verify all succeed over -p/-P $VPS_SSH_PORT. There's no automated coverage for this path.
