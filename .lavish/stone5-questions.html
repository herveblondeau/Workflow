Where the app is right now (stones 1–4): Main.Api hosts PDF watermarking (POST /api/watermark → token → GET /api/download/{token}), guarded by X-Api-Key. Main.Api/.env already has API_KEY set. Two ways to test:

A — API directly (fastest):
1. cd Main.Api && dotnet run --launch-profile https (reads .env)
2. curl -k -H "X-Api-Key: $KEY" -F "file=@in.pdf" -F "watermarkType=Invisible" -F "contentType=Custom" -F "customText=HELLO" https://localhost:7156/api/watermark
3. curl -k -H "X-Api-Key: $KEY" -L -o out.pdf https://localhost:7156/api/download/<token>
($KEY = the value in Main.Api/.env)

B — full local frontend → local API (the "local only" flow):
1. Terminal 1: cd Main.Api && dotnet run --launch-profile http (→ :5261)
2. Terminal 2: cd ../filigrane/frontend && WORKFLOW_API_KEY=$KEY npm run dev
3. Open the printed URL, upload a PDF, watermark it. DevTools Network shows no X-Api-Key on the browser's own request — the vite proxy injects it server-side.

C — local frontend → prod API (also fine & safe): same as B but point the proxy at the deployed API:
WORKFLOW_API_URL=https://<domain> WORKFLOW_API_KEY=$KEY npm run dev
Only you reach the local frontend and the key stays on your machine, so this is still the "local only" case. Not the blocked one — that's serving the frontend itself publicly to strangers.

Where nginx fits: filigrane's own production nginx is the prod analog of the vite proxy — it would serve the built frontend and inject X-Api-Key when proxying /api/*. It's currently unwired (deferred). It only matters when serving the frontend to others; for flows B and C, vite is your proxy and nginx never appears.

1. What is stone 5? (really: who reaches the frontend?)

Everything hinges on one fork. There's a single shared API_KEY, and nginx/proxy injects it server-side — the visitor presents nothing — so the key means "this is filigrane", not "this is user X". Per-user keys (LLM-style) would mean each user mints and presents their own key, which is building user auth. Given that:

You just said local-only — that unblocks nothing new and makes stone 5 anonymization. Only pick a network option if you actually want others reaching the frontend now.

2. What does "strip metadata" cover?

PDFs carry two metadata layers, and they're different code paths.

Recommend both: "anonymize" that leaves XMP intact would surprise users and defeat the point.

3. Endpoint & delivery shape

Watermarking already has a token flow and storage/cleanup service.

Recommend mirroring: reuses the token/storage/cleanup plumbing, keeps each tool's contract clean.
