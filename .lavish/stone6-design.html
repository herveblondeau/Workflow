1. Exposure — the "which humans" gate

This is the boundary the journal flagged. The shared X-Api-Key says "this is filigrane", not "this is an allowed user", so anything network-reachable needs a gate deciding which humans get in — unless nobody outside can reach it at all.

Loopback-only keeps the "no auth" promise intact and proves the whole stack runs on the VPS. If you want it actually reachable now, edge-gating is the honest way without app auth.

2. Same VPS as Main.Api, or a separate host?

Stone 3 established "API and clients on separate hosts". Co-locating filigrane departs from that — but keeps Main.Api entirely private.

Same-host is the pragmatic first deploy and keeps the API private on the box. Splitting hosts is a natural later stone if a second real client appears.

3. How does filigrane get deployed?

Main.Api uses deploy/provision.sh (a re-runnable SSH/clone/compose wizard) + deploy/docker-compose.yml, from stone 4.

A filigrane-owned wizard matches the established stone-4 pattern and keeps each repo deployable on its own.
